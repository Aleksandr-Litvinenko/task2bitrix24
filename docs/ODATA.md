# Интеграция с 1С:УНФ через OData

Как taskCRM подключается к 1С:Управление нашей фирмой, что именно создаёт и как это устроено внутри. Весь код — в [`unf.php`](../unf.php); константы — в [`config.php`](../config.php).

Зачем это нужно: отчёт «Закрытые часы» уже знает, сколько часов закрыл каждый сотрудник за месяц. Раньше эти же цифры руками переносили в УНФ документами. Две кнопки на главной делают это за один клик.

---

## 1. Как подключаемся

### Точка входа

Стандартный OData-интерфейс 1С (`standard.odata`). База в 1С:Фреш:

```text
https://1cfresh.com/a/sbm/<номер-базы>/odata/standard.odata
```

Задаётся переменной окружения `UNF_ODATA_BASE_URL` либо константой `LOCAL_UNF_ODATA_BASE_URL` в `config.local.php`.

**Предварительно в самой УНФ должна быть включена публикация OData** и заведён отдельный пользователь с правом на неё. Логин и пароль — `UNF_ODATA_USER` / `UNF_ODATA_PASSWORD` (или `LOCAL_*` в `config.local.php`, файл в `.gitignore`). Без них кнопки УНФ не работают, но всё остальное приложение работает нормально.

### Транспорт

Единственная функция `unfOdataRequest($method, $path, $payload, $params)`:

- **HTTP Basic** — заголовок `Authorization: Basic base64(user:password)` собирается вручную на каждый запрос, сессия не держится;
- `Accept: application/json`, у запросов с телом — `Content-Type: application/json; charset=utf-8`;
- тело кодируется с `JSON_UNESCAPED_UNICODE | JSON_UNESCAPED_SLASHES` — кириллица уходит как есть, а не `\uXXXX`;
- `curl` при наличии расширения, иначе fallback на `file_get_contents()` со stream context (`ignore_errors = true`, чтобы прочитать тело ошибки);
- таймауты: 20 секунд на соединение, 180 на ответ — документы проводятся не мгновенно;
- метод (`GET` / `POST`) передаётся как `CURLOPT_CUSTOMREQUEST`, поэтому одна функция обслуживает и чтение, и запись, и вызов `Post()`.

Путь собирается `unfOdataUrl()`: каждый сегмент проходит `rawurlencode()` — имена сущностей кириллические (`Document_УчетВремени`), без кодирования запрос до 1С не доедет. Query-параметры кодируются по `PHP_QUERY_RFC3986`.

### Разбор ответа

- `unfOdataValues()` достаёт коллекцию из `value` (OData v3/v4) или `d.results` (старый формат) — код не зависит от версии интерфейса;
- `unfOdataEntity()` так же разворачивает одиночную сущность из `d`;
- статус `>= 400` превращается в исключение, текст берётся `unfOdataErrorMessage()` — она перебирает `error.message.value`, `error.message`, `odata.error.message.value`, `odata.error.message` и откатывается на `HTTP <код>`. 1С отдаёт ошибку в разных обёртках, и без этого перебора наружу шло бы бесполезное «HTTP 400».

Ошибка любого запроса не роняет всю операцию: она ловится на уровне одного сотрудника и попадает в список `errors` результата — остальные документы создаются.

### Проверка связи

```bash
php tools/preflight.php --online
```

В блоке «1С:УНФ: доступность OData» — успешный ответ и число сотрудников в справочнике.

## 2. Справочник сотрудников и сопоставление ФИО

Прежде чем создать документ, нужно превратить строку отчёта (Bitrix user ID + ФИО) в `Ref_Key` сотрудника УНФ.

`unfFetchEmployees()` читает `Catalog_Сотрудники` постранично (`$top=500` + `$skip`), выбирая `Ref_Key`, `Description`, `DeletionMark`; помеченные на удаление отбрасываются. Результат кешируется в статической переменной на время запроса — справочник читается один раз, а не на каждого сотрудника.

`unfFindEmployeeForReportRow()` ищет соответствие в четыре шага:

1. **Ручная карта** `UNF_EMPLOYEE_KEY_MAP` — ключом может быть Bitrix user ID, ФИО из отчёта или нормализованное ФИО. Это способ разрулить любой нестандартный случай без правки кода.
2. **Точное совпадение нормализованного ФИО.** Нормализация (`unfNormalizeName()`): `ё → е`, нижний регистр, всё кроме букв и цифр заменяется пробелом, пробелы схлопываются. «Иванов И.И.» и «иванов и и» становятся одной строкой.
3. **Совпадение по набору слов.** ФИО режется на токены, они сортируются, и ищутся сотрудники УНФ, у которых **все** токены из Битрикса присутствуют (`unfTokensAreSubset()`). Так «Иванов Иван» находит «Иванов Иван Иванович» — в Битриксе часто нет отчества.
4. Если подошёл ровно один — берём его. Если несколько — исключение со списком кандидатов (лучше не создать документ, чем создать не тому). Если ни одного — исключение с подсказкой добавить запись в `UNF_EMPLOYEE_KEY_MAP`.

## 3. Что создаём

### 3.1. Учёт времени — `Document_УчетВремени`

Кнопка **«Создать Учеты времени»** (`unf_time.php` → `createUnfTimeDocumentsForReport()`).

**Период.** Документ датируется последним днём отчётного месяца, 12:00. Сам учёт заполняется за **первую полную неделю месяца**: `ДатаС` — первый понедельник (или 1-е число, если это понедельник), `ДатаПо` — плюс 6 дней. Если полная неделя в месяц не помещается, операция останавливается с понятной ошибкой.

**Распределение часов по дням** (`unfDistributeHours()`): месячная сумма укладывается в дни недели подряд, по 24 часа максимум в день — Пн 24, Вт 24, Ср остаток и так далее. Такой формат нужен самой УНФ: она хранит длительность по дням недели.

**Если часов больше 168**, в одну строку табличной части они не влезают (7 дней × 24 часа). Тогда добавляется **вторая строка «Операций»**, и остаток раскладывается в ней снова с понедельника. При необходимости строк будет больше — по 168 часов на каждую.

Например, 168.5 ч дают две строки: первая — по 24 часа на каждый день недели (`Всего` 168), вторая — 0.5 часа в понедельник (`Всего` 0.5). Именно так документ заполняется руками; эталон — КДНФ-000085. У пустых дней второй строки и начало, и окончание равны `0001-01-01T00:00:00`.

Предохранитель `UNF_TIME_MAX_OPERATION_ROWS` (10 строк, то есть 1680 часов) ограничивает разрастание: в месяце физически не больше 744 часов, поэтому превышение означает испорченные списания, а не реальную работу — в этом случае документ не создаётся с понятной ошибкой. Молча урезать часы в документе, по которому выставляется счёт, нельзя.

Дополнительно заполняется время «с» / «по» на каждый день (`ПнВремяНачала` / `ПнВремяОкончания` и так далее): начало — всегда `0001-01-01T00:00:00`, окончание — то же «нулевое» число плюс длительность. 24 часа записываются как `23:59` — сутки в это поле не влезают, а фактическая величина всё равно лежит в `Длительность`.

**Тело документа:**

| Поле | Значение |
|---|---|
| `Date` | последний день месяца, 12:00 |
| `ДатаС` / `ДатаПо` | первая полная неделя месяца |
| `Организация_Key` | `UNF_TIME_ORGANIZATION_KEY` |
| `СтруктурнаяЕдиница_Key` | `UNF_TIME_STRUCTURAL_UNIT_KEY` |
| `Сотрудник_Key` | найденный `Ref_Key` |
| `Автор_Key` | `UNF_TIME_AUTHOR_KEY` |
| `ХозяйственнаяОперация_Key` | `UNF_TIME_BUSINESS_OPERATION_KEY` |
| `Комментарий` | тег `#Загружено_task2`, часы, период, Bitrix user ID и ФИО |
| `Операции` | одна строка: `ВидРабот_Key`, `Номенклатура_Key` («Работа консультанта 1С»), `ВидЦен_Key`, `Расценка` (`UNF_TIME_RATE`, по умолчанию 0), `Всего` = часы, длительности и времена по дням недели, `Сумма` = расценка × часы |

**Проведение.** Документ создаётся с `Posted: false`, затем, если `UNF_TIME_POST_DOCUMENTS` включён (по умолчанию да), вызывается стандартное действие OData:

```text
POST Document_УчетВремени(guid'<Ref_Key>')/Post()
```

Поставьте `LOCAL_UNF_TIME_POST_DOCUMENTS = false`, чтобы документы только записывались — удобно для первого прогона.

### 3.2. Задание на работу — `Document_ЗаданиеНаРаботу`

Кнопка **«Создать Задания на работу»** (`unf_workorder.php` → `createUnfWorkOrdersForReport()`).

Это план на следующий месяц, посчитанный от факта текущего.

**Период.** Документ датируется **1-м числом следующего месяца**, 12:00; `ДатаНачала` — то же 1-е число, `ДатаОкончания` — последний день этого следующего месяца.

**План.** `Трудоемкость` = факт закрытых часов × `UNF_WORK_ORDER_UPLIFT` (по умолчанию `1.1`, то есть +10%). `Цена` = `UNF_WORK_ORDER_RATE` (4500 ₽), `Сумма` и `СуммаДокумента` = цена × план.

**Тело документа** повторяет реально заполненный в УНФ документ-образец: `ВидОперации = 'Внешнее'`, `ПоложениеВидаРабот = 'ВШапке'`, `Состояние_Key`, `КалендарьСотрудника_Key`, `ХозяйственнаяОперация_Key` (своя, отличная от учёта времени), плюс табличная часть `Работы` с одной строкой. Организация, структурная единица, вид работ, номенклатура и вид цен — те же константы, что и у учёта времени.

Комментарий тоже помечен `#Загружено_task2` и содержит план, факт и Bitrix user ID.

## 4. Как это устроено в целом

### Поток данных

```text
Битрикс24                       taskCRM                          1С:УНФ
─────────                       ───────                          ──────
задачи + списания   ──►  buildClosedHoursReport()
                              (часы по сотрудникам)
                                    │
                                    ├──►  unfFetchEmployees()   ──►  Catalog_Сотрудники
                                    │     сопоставление ФИО ──► Ref_Key
                                    │
                                    ├──►  проверка дубля       ──►  GET  Document_… ($filter)
                                    │
                                    ├──►  создание             ──►  POST Document_…
                                    │
                                    └──►  проведение           ──►  POST …/Post()
```

Источник цифр — тот же самый отчёт, который уходит в Excel. Отдельного расчёта для УНФ нет, поэтому Excel и документы всегда сходятся.

### Идемпотентность

Перед созданием документ ищется по ключевым полям:

- учёт времени — `Сотрудник_Key` + точное совпадение `ДатаС` и `ДатаПо`;
- задание на работу — `Сотрудник_Key` + `ДатаНачала`.

Если такой документ есть, сотрудник уходит в `skipped` с его номером — дубль не создаётся. **Кнопку можно нажимать повторно без последствий**: это главная защита, потому что операция не транзакционная и на середине может прерваться.

Сотрудники с нулевыми часами тоже попадают в `skipped` — пустые документы не нужны.

### Результат операции

Обе функции возвращают одинаковую структуру, её показывает интерфейс:

```text
ok       — не было ни одной ошибки
period   — отчётный месяц
unf_period — даты документа (date, date_from, date_to)
created  — [ФИО, часы, номер документа, Ref_Key, проведён ли]
skipped  — [ФИО, часы, причина: нулевые часы / документ уже есть]
errors   — [ФИО, часы, текст ошибки]
```

Ошибка на одном сотруднике не останавливает остальных.

### Все документы помечены

Комментарий каждого созданного документа начинается с `#Загружено_task2`. По этому тегу в УНФ находится всё, что создано автоматикой, — и при разборе, и если понадобится массово удалить неудачный прогон.

### Константы

GUID-и справочников (организация, структурная единица, вид работ, номенклатура, вид цен, хозоперация, состояние, календарь, автор) зашиты в `config.php` значениями по умолчанию для конкретной базы и переопределяются через окружение или `config.local.php`. Значения для «Задания на работу» взяты из реально заполненного документа-образца — если в базе поменяются виды операций или состояния, менять нужно именно их.

## 5. Что может пойти не так

| Симптом | Причина и что делать |
|---|---|
| `Не настроены UNF_ODATA_USER и UNF_ODATA_PASSWORD` | нет логина/пароля в окружении или `config.local.php` |
| `HTTP 401` | неверные учётные данные либо у пользователя нет права на OData |
| `HTTP 404` на сущности | не опубликован OData или сущность в базе называется иначе |
| `Не найден сотрудник УНФ для "..."` | ФИО в Битриксе и УНФ расходятся — добавьте запись в `UNF_EMPLOYEE_KEY_MAP` |
| `Найдено несколько сотрудников УНФ для "..."` | однофамильцы — снимается той же картой соответствий |
| `Документ за эту неделю уже есть` | не ошибка: защита от дублей отработала |
| `В выбранном месяце не найдена полная неделя` | редкий край календаря — учёт времени за такой месяц не создать |
| `Не удалось разложить … ч: это больше 1680 часов` | в месяце столько часов быть не может — проверьте списания в Битриксе. До 1680 ч раскладываются сами, добавлением строк |

Логи ошибок PHP на сервере пишутся туда, куда настроен `error_log` пула PHP-FPM.
